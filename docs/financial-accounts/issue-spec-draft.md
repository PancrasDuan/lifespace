# 财务账户系统：账户管理、余额与关联转账

## 问题（Problem Statement）

财务页目前以手工账户名称记录流水，缺少实际存放资金的交易账户及其当前余额。使用者希望管理银行卡、微信零钱、支付宝余额、饭卡等资金容器，让每笔收支有明确归属，并能在本人账户间转账。

## 方案（Solution）

在现有财务页采用已选定的 A 布局：上方平铺交易账户卡片，下方保留流水表格。提供本人账户列表、新增、修改名称、手工修正余额和关联转账；现有收支、退款和删除操作联动当前余额。需求、原型和技术方案均已确认实施。

## 用户故事（User Stories）

1. 作为财务页使用者，我希望管理实际存放资金的交易账户，以便区分银行卡、零钱和饭卡中的钱。
2. 作为财务页使用者，我希望只访问本人的账户和流水，以便保持不同使用者的数据隔离。
3. 作为财务页使用者，我希望在流水上方看到账户卡片和当前余额，以便一起查看账户与明细。
4. 作为财务页使用者，我希望新增有名称和初始余额的账户，以便开始使用账户系统。
5. 作为财务页使用者，我希望本人账户名称不重复，以便选择账户时能明确区分。
6. 作为财务页使用者，我希望初始余额可以为零、正数或负数，以便按实际情况建账。
7. 作为财务页使用者，我希望改名后关联流水显示账户新名称，以便统一使用当前名称。
8. 作为财务页使用者，我希望改名保持账户标识和余额，以便不改变流水归属及金额。
9. 作为财务页使用者，我希望能直接修正当前余额，以便校正实际资金差异。
10. 作为财务页使用者，我希望修正余额保留内部记录且不显示为收支，以便流水仍表示真实交易。
11. 作为财务页使用者，我希望过时的余额表单提示核对最新金额并保留输入，以便避免覆盖期间发生的交易。
12. 作为财务页使用者，我希望新收支必须选择本人交易账户，以便明确实际扣款或到账位置。
13. 作为财务页使用者，我希望收支及补录交易按金额增减当前余额，以便账户反映录入结果。
14. 作为财务页使用者，我希望退款固定归属父支出的账户和分类，以便保持原交易关系。
15. 作为财务页使用者，我希望删除流水撤销其余额影响，以便能修正误录。
16. 作为财务页使用者，我希望删除支出及其退款时按净额撤销，以便余额符合实际被删除的范围。
17. 作为财务页使用者，我希望在两个不同的本人账户间填写一份金额、时间和可选备注，以便记录资金转移。
18. 作为财务页使用者，我希望转账生成等额相反且关联的转出、转入流水，以便查看两侧资金变化。
19. 作为财务页使用者，我希望两侧流水与余额一起保存成功，以便不会留下半笔转账。
20. 作为财务页使用者，我希望能从转账流水查看对应另一侧，以便核对同一次转账。
21. 作为财务页使用者，我希望误录转账时整组删除并撤销两边余额，以便重新录入正确内容。
22. 作为财务页使用者，我希望重试保存不重复记账或扣款，以便在结果不明确时安全重试。
23. 作为财务页使用者，我希望金额超限时整次操作拒绝，以便避免部分成功或金额被截断。
24. 作为财务页使用者，我希望已关联账户的新流水正常可用，旧流水待归属迁移后再开放，以便分开完成建系统和旧数据迁移。
25. 作为财务页使用者，我希望桌面和手机都能完成这些操作，以便沿用现有财务页的使用方式。

## 实施决定（Implementation Decisions）

- 复用现有 React / TypeScript、Worker、Supabase、在线身份核验与所有者隔离，业务仍通过受控 RPC 访问数据库。新增表开启 RLS，沿用固定函数搜索路径和受限执行权限。
- 复用原流水表和所有者版本表，新增账户表与内部余额修正记录表，共四表；不增加转账表。
- 交易账户使用稳定 UUID，同一所有者下名称唯一，去除首尾空白，长度为 1–50 个 Unicode 码点。
- 流水新增 `account_id`、`transfer_id`；同一次转账两侧共享 `transfer_id`。同所有者账户外键、转账方向唯一约束及不可变字段保护配合受控事务，保证引用和配对完整。
- 旧 `account_name` 保留原内容并解除非空要求，供后续迁移使用；新流水只保存账户 ID，读取时关联账户当前名称。
- `category_code` 仅增加 `transfer_in`（转入）、`transfer_out`（转出），原分类保留；`direction` 继续为收入、支出。普通创建接口不能生成转账单侧。
- 新增账户查询、创建、修改与转账创建接口；普通创建改用账户 ID。沿用原流水查询、退款、删除预览和删除入口，详情及删除预览支持对侧转账流水。
- 账户余额与交易金额使用整数分。余额范围为 ±99,999,999,999 分（±999,999,999.99 元），允许零、负数和最多两位小数；流水及转账金额沿用现有限额，非零，转账表单填写正数。
- 开户直接设置初始余额；收支、退款、补录和转账按有符号金额增减当前余额，删除撤销对应影响。余额不足不限制操作，结果超限则整次拒绝并回滚。
- 手工修正直接校正当前金额，不改变旧流水，不计收支，内部记录保留但不展示。已确认示例：1,000 元记支出 20 元后为 980 元，手工改为 900 元，再删除此前支出，余额为 920 元。
- 修改仅提交实际改变的字段。改名不回写余额；修正余额携带读取时的金额校验，期间已变化则提示核对最新余额并保留输入。无实际变化不产生修正记录或版本推进。
- 普通支出退款固定继承父账户和分类，其余退款规则沿用现状。删除支出及其退款统一撤销净额，例如 −100 元支出及 +30 元退款一起删除，余额增加 70 元。
- 转账限两个不同的本人账户，一次生成支出／转出和收入／转入两条等额相反流水，并联动两边余额。转账不属于个人真实收支，不支持退款；录错时整组删除重录，实际转回资金另记反向转账。
- 转账两侧必须一起新增、一起删除。删除仍核对具体影响范围，无关写入不使确认失效，重复删除不再次改余额。
- 所有实际写入复用所有者写锁，将账户、流水、修正记录和版本作为一个短事务提交。所有者版本表不改字段，一次业务写入只推进一次版本；两条转账不计成两次操作，重试和无变化不重复推进。
- 创建账户保存原请求号及规范化输入摘要；所有成功的账户修改（含纯改名和无变化）在账户表内保留请求摘要，余额修正表仍只记录实际金额变化。转账一次提交一个请求号，转出行保存该号，转入行使用内部请求号，两行共享独立转账标识。重试核对原输入并复用原结果，不重复写入或扣款，已删除请求不复活；同号不同输入拒绝。
- 前端查询按所有者隔离，进入页面、重新聚焦及成功写入后刷新相关账户、流水和详情，保留正在填写的表单。原型模拟数据和调试工具不进入正式页面。
- 未归属旧流水在列表、详情、关联读取及正常操作中统一隐藏，保留原数据。准备可审阅和可在隔离数据库重放的结构升级 SQL；与配套函数及代码协调发布，执行顺序和回退步骤随最终 SQL 与 PR 核对。

## 测试决定（Testing Decisions）

- 沿用已确认的最高接缝：正式页面 → 真实 Worker → 隔离 PostgreSQL / PostgREST，只控制测试身份及本机数据库地址。复用现有账单数据库、接口与浏览器测试模式。
- 测试观察持久化结果、接口行为、余额和页面交互，不以模拟业务 RPC 或镜像实现的断言代替真实事务验证。
- 覆盖账户新增、名称唯一、刷新持久化、改名现名展示、零和负余额、上下界、改名不覆盖余额、修正冲突及重试、内部记录和所有者隔离。
- 覆盖普通收支、退款及删除净额的余额联动，旧流水保留但不可正常读取或操作。
- 覆盖转账成对增删及余额原子性、对侧查看、单侧创建拒绝、请求去重、已删除请求不复活、跨所有者拒绝和失败回滚。
- 覆盖 A 布局的桌面及手机实际交互，并回归原有日期、分页及其他受影响页面。
- 默认 CI 不启动真实数据库套件；实施必须显式运行数据库与浏览器全链路并记录实际通过结果，不能将跳过算作通过。执行密钥扫描、适当类型检查、构建和安全回归。

## 本期不包含（Out of Scope）

- 账户停用、重新启用、账户删除、按账户筛选及余额修正记录的展示。
- 旧数据自动归属、按旧名称建账户或匹配账户、旧字段清理；上线后单独进行数据库归属迁移。
- 转账单侧删除、转账退款或独立转账表。
- 原型作为正式业务实现直接交付。
