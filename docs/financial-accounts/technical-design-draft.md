### 转账组标识示例

`transferId` 是接口中的命名，数据库新增字段为 `ledger_entries.transfer_id`。每条转账流水仍有自己的流水标识，两侧额外共享同一个转账组标识；普通收支和退款的转账组标识为空。

例如账户 A1（银行卡）向账户 A2（饭卡）转账 100 元，示意金额使用元，实际继续按整数分存储：

| 流水标识 | 账户标识 | 收支类型 | 分类 | 金额（元） | 转账组标识 |
| --- | --- | --- | --- | --- | --- |
| E1 | A1 | 支出 | 转出 | -100 | T1 |
| E2 | A2 | 收入 | 转入 | +100 | T1 |

通过 T1 可以找到同次转账的两条流水，用于关联查看与成对删除。它不替代账户标识或单条流水标识，也不增加一张转账表；另一笔转账即使内容相同，也使用不同的组标识。

这一方案复用原明细体系，适合本期两侧固定的转账范围。独立转账表可提供额外请求记录与外键锚点，但会增加一个实体；共享组标识则需要明确保障两侧完整性及操作去重，不能仅新增字段。

继续复用现有所有者行锁，把流水、账户余额、内部修正记录及版本的写入放进一次短数据库事务。事务范围不包含外部请求或使用者确认过程。

| 不可变字段保护 | 将账户标识、转账组标识纳入保护 | 日常操作不能修改已创建流水的账户归属或转账配对关系 |

`ledger_owner_revision` 不改字段结构，继续使用所有者、版本、创建时间和更新时间。账户新增、实际改名、余额修正以及流水增删都纳入原有写锁与版本更新范围；一次实际业务操作只推进一次版本，两条转账不计成两次独立版本变化，重复请求或无实际变更不重复推进。

配套读写函数也需调整：查询仅开放已归属流水，关联账户读取当前名称；普通创建与退款同步增减所属账户余额；退款继承父账户标识并排除转账；删除普通支出时统一计算父子退款的余额撤销，删除转账则处理两侧；删除预览同时展示对应影响范围。旧未归属流水不通过列表、详情、关联入口或正常业务操作暴露，留待上线后的专门迁移处理。

旧数据回填和旧名称列的最终清理属于后续迁移，不在本次结构调整中执行。实际迁移时另行处理不可变字段保护与数据核验，不开放日常修改历史流水归属的功能。

## 已确认：账户修改的并发处理（Q33）

账户修改仅提交实际改变的字段，改名不顺带写回表单中的旧余额。明确修正余额时，提交读取表单时的余额作为校验；若期间余额已发生变化，则保留输入、返回最新余额，提示重新核对后再提交。

例：打开表单时余额为 1,000 元，另一笔支出使余额变成 900 元。只改名时应保持 900 元；若同时修正金额，应先核对最新余额。现有事务锁能串行化写入，但不能自行判断表单中的 1,000 元是否过时。

用户已确认这一修改规则。四表数据组织及旧表调整也已确认，架构决定见 [ADR 0008](../adr/0008-ledger-account-storage.md)。

## 已确认：转账去重（Q35）

一笔转账由前端提交一个稳定 `requestId`，页内重试继续使用它。转出流水保存这个请求号，转入流水由数据库分配独立的内部请求号，以沿用现有每行请求号唯一约束；两行额外共享数据库生成的 `transfer_id`。

重复提交先通过原请求号定位转出记录，再按转账组读取两侧并核对原输入；相同请求返回原来两条流水的结果，不重复更新余额。已删除的原请求也不重建流水。完整原子写入保证不会由同次转账留下单侧记录，无需另加转账主表或请求记录表。

## 已确认：账户余额金额上限（Q36）

现有单笔流水绝对值上限为 999,999,999.99 元，采用整数分传输、计算和存储。账户初始余额、修正后的余额以及流水联动后的余额采用相同绝对值上限，允许零、正数与负数，最多两位小数。

余额联动结果超出范围时，整次操作拒绝并回滚，不截断金额或只保存部分流水。前端、Worker 和数据库执行一致校验；单笔流水、退款与转账金额仍须非零，账户余额可以为零。

## 新表字段细化

以下为已确认四表组织的实现细化，字段名在编写共享契约与 SQL 时保持一致。

### 账户表 `ledger_accounts`

| 字段 | 类型与职责 |
| --- | --- |
| `id` | 数据库生成的 UUID，账户稳定身份 |
| `owner_id` | 所有者 UUID，引用现有所有者版本行 |
| `name` | 去除首尾空白后的账户名称，1–50 个 Unicode 码点；同所有者下唯一 |
| `balance_cents` | `bigint`，当前整数分余额，范围为 ±99,999,999,999 分 |
| `request_id` | 创建账户的原请求号，同所有者下唯一，后续改名或修正余额不改它 |
| `request_hash` | 规范化创建输入的摘要，用于重试时核对原输入；避免拿已修改的现名或余额当创建原值 |
| `update_requests` | 内部 JSONB 映射：成功修改的请求 UUID → 规范化输入 SHA-256，含纯改名和无变化请求；不对外返回 |
| `created_at`、`updated_at` | 服务端生成的时间 |

保留 `(owner_id, id)` 唯一关系供同所有者外键引用。初始余额直接设定，不生成普通收入流水。零余额可以创建；余额不足不构成转账或支出的拒绝理由，只校验最终数值是否在已确认范围内。

### 余额修正表 `ledger_balance_adjustments`

| 字段 | 类型与职责 |
| --- | --- |
| `id` | 数据库生成的 UUID |
| `owner_id`、`account_id` | 同所有者账户关联 |
| `before_cents`、`after_cents` | 本次实际修正前后金额，均为整数分 |
| `request_id`、`request_hash` | 同次修正的页内去重及原输入核对；摘要覆盖同次提交中的实际修改字段 |
| `created_at` | 服务端记录时间 |

该表只追加内部修正记录，不提供页面列表。只改名、提交相同余额或其他无实际变更时不新增余额修正记录，也不推进版本。已完成修改的重试先查账户内请求摘要，再检查当前余额，避免再次覆盖后续收支结果。

### 账户修改请求的生命周期与代价（#118 评审修复）

全部成功的账户 PATCH（纯改名、混合修改、余额修正及无变化）统一在 `ledger_accounts.update_requests` 追加摘要。摘要包含原账户 ID 及实际提交的规范化字段，包括余额旧值校验；字段的存在与否也参与核对。同所有者写锁覆盖跨账户的查重与追加，同号异输入或异账户返回 `REQUEST_ID_REUSED`，同号同输入返回原账户 ID 与当前版本，在余额旧值校验之前结束，因此不重放旧名称或余额。不同所有者的请求号相互独立。

元数据与账户、修正记录、所有者版本在同一事务提交，失败不占用请求号。无业务变化只追加元数据，不更新账户或所有者的业务修改时间、不推进版本、不新增修正记录。已有摘要由账户不可变触发器保护，不能删除或替换；表继续开启 RLS 并撤销所有业务角色的直接访问，唯一写入入口仍是服务角色可调用的受控 RPC。公开序列化及接口契约不变，四表职责与 `owner_revision` 字段不变。

摘要随账户保留，不按时间或数量淘汰；本期无账户删除功能，淘汰会令旧请求重新应用。GIN 索引支持按请求号定位账户，再核对所有者与摘要；数据库可按数据分布选择所有者索引，不能依赖 JSONB 索引提供跨行唯一约束，同所有者唯一性由受控权限和所有者锁共同保证。存储与索引随成功的不同请求数线性增长，每次追加需要重写该账户的 JSONB，额外产生 WAL、索引维护及逐渐增长的写入成本；无变化请求也占空间。这是保留四表且修改频率较低时的取舍，不是通用高频命令日志；规模增长需要重新评估存储组织并另行确认，不静默截断记录。余额修正表仍只保存实际金额变化，原请求字段保留用于修正事实核对。

此次修正更新尚未发布的 `accounts.sql` 一次性安装稿，沿用已确认的两表升级为四表的执行顺序，并在隔离数据库重放；不得在已安装旧版四表的环境直接重复执行该建表脚本。旧版没有保存的纯改名／无变化请求无法追溯生成，已有旧版测试环境应重建隔离库。生产尚未执行本期结构升级；若部署目标已安装旧稿，须先另行审阅增量升级与历史请求边界，不把重建测试库作为生产操作。

## 接口契约细化

金额字段均为整数分的 JSON 整数；标识均为 UUID；交易时间沿用精确到秒的 UTC ISO 表达，解释与展示仍使用北京时间。客户端不能提供所有者、状态或自行指定转账关联。

| 接口 | 请求要点 | 成功结果 |
| --- | --- | --- |
| `GET /api/ledger/accounts` | 不接受其他使用者的标识 | `accounts`（账户 ID、名称、当前余额、时间）及 `version` |
| `POST /api/ledger/accounts` | `requestId`、`name`、`balanceCents` | `accountId`、`version` |
| `PATCH /api/ledger/accounts/:id` | `requestId`；实际变化的 `name` 或 `balanceCents`；修正余额时携带 `expectedBalanceCents` | `accountId`、`version`；余额已变化时返回冲突并重读最新账户，保留表单输入 |
| `POST /api/ledger/transfers` | `requestId`、`fromAccountId`、`toAccountId`、正数 `amountCents`、`occurredAt`、可选 `note` | `transferId`、`outEntryId`、`inEntryId`、`version`、`deleted` |
| 原 `POST /api/ledger/entries` | 普通流水改传 `accountId`，不再接受手填账户名 | 保留现有流水回执 |
| 原退款接口 | 仍只接收金额、时间与备注，不接受改选账户 | 保留现有回执，退款继承父流水的账户 ID |
| 原查询、详情接口 | 沿用日期、分页与版本参数，不增加账户筛选 | 流水增加 `accountId`、可空 `transferId`；`accountName` 由账户表关联计算 |
| 原删除预览与删除接口 | 沿用目标流水与具体影响范围确认 | 转账预览补充对侧流水；删除仍返回现有回执 |

普通新建接口仅接受普通分类，不能使用转入、转出创建单侧流水。两项转账分类只由转账事务生成。转账详情增加可空的 `transferEntry` 以查看对侧；退款父关联、退款列表及原有状态规则继续保留。

同请求号不同输入拒绝复用；重复成功写入不重新推进版本。账户改名按字段执行更新，不回写未修改的余额；结果不明确时可重读账户，继续沿用现有页面内处理方式。错误区分输入无效、账户不存在或非本人、名称重复、余额已变化、请求号复用、列表变化、删除范围变化和上游结果未确认。

## 事务与删除行为

所有写入先建立或取得本人所有者版本行，再在短事务内取得现有写锁。账户、流水、内部修正记录与版本作为整体提交，失败全部回滚。

| 操作 | 同一事务内的效果 |
| --- | --- |
| 新建账户 | 查重、检查名称、写入当前余额及创建元数据、推进版本 |
| 修改账户 | 核对实际修改字段；修正余额时检查旧值、写内部记录；应用变化后推进版本 |
| 普通收支、退款 | 写入流水并按有符号金额更新所属账户余额；退款沿用原额度、时间和父支出规则 |
| 转账 | 校验两个不同的本人账户，写两条关联流水，分别扣减和增加余额，只推进一次版本 |
| 普通流水或退款删除 | 逻辑删除实际确认范围，撤销这些流水的余额影响 |
| 转账删除 | 找齐同组两条，逻辑删除两侧，并撤销两个账户对应的余额影响 |

删除普通支出时，原支出与关联退款一起计算撤销金额。例如 −100 元支出与 +30 元退款同时删除，该账户增加 70 元。删除确认范围仍按具体流水集合核对，无关的新建或账户修改不使删除确认失效。重复删除不再次调整余额或推进版本。

## 前端与刷新

正式财务页按已确认 A 布局增加账户区，复用现有导航、弹窗、交易时间控件、身份上下文和请求封装。账户查询使用同一所有者的 `ledger` 缓存前缀，页面进入和实际写入后重新读取相关账户、流水与详情；从隐藏恢复可见时按各活动查询的成功更新时间判断，超过一分钟或读取失败则刷新，手动刷新不受时限。账户改名后，关联流水显示当前名称；刷新数据保留正在填写的表单。

账户和流水按已有接口分别读取，继续采用写后刷新方式。原型中的模拟数据、重置入口与数据状态工具只用于设计核对，不进入正式业务页面。

## 权限与上线结构兼容

新增表开启 RLS 并沿用当前受控函数访问方式，业务角色不直接修改表。Worker 从在线核验身份注入所有者，RPC 继续显式限定所有者；函数执行权限与固定搜索路径沿用现有约定，客户端不能越权引用账户或转账组。

结构升级保留原流水与旧名称内容，增加可空账户标识等兼容字段。新写入必须属于有效本人账户，名称不在新流水中重复保存。列表、详情、退款关联以及正常写入目标统一排除未归属旧流水。

编写可审阅、可在隔离数据库重放的结构升级 SQL；结构升级、配套函数与新代码在同一次发布中协调上线，执行顺序和回退步骤随最终 SQL 与 PR 一并核对。旧数据归属回填及旧名称列清理仍留到上线后单独处理，不作为本轮自动动作。

## 验证与交付安排

主接缝沿用正式页面 → 真实 Worker → 本机隔离 PostgreSQL / PostgREST，只控制测试身份和数据库地址。扩展现有隔离执行器加载账户结构与新套件，显式执行：

```bash
npm run check:secrets
npm run build:ci
npm run test:database -- --ledger --browser
npm run test:browser
```

当前 `.github/workflows/ci.yml` 的 `validate` 不启动隔离数据库。缺少数据库地址时相关 API、浏览器套件会跳过，因此必须另行保存真实数据库套件的实际通过记录，不把默认 CI 通过或跳过视作数据库验证完成。

重点验证：

- 账户新增、名称重复、改名后现名展示、负余额与金额上下界；刷新后数据仍存在。
- 改名不覆盖余额，余额已变化时的修正确认，内部记录及重复提交结果。
- 普通收支、退款、删除父支出及退款时的余额净影响。
- 转账两条及余额一起新增、一起删除；单侧创建拒绝，重复提交不多写，已删请求不复活，事务失败无部分结果。
- 旧流水保留但不可读取或通过正常接口操作，其他使用者的账户与流水不能被引用。
- A 布局及新增、修改、转账、关联查看、删除在桌面与手机上的真实交互；原有日期、分页与其他页面回归。

本任务交付分级为“需确认的变更”，依据是持久化结构、余额规则及业务接口调整。实施后完成适当检查、最终提交的双轴评审、用户界面验收及必需 CI，再取得具体合并发布授权；部署验收后关闭 Issue。技术方案确认不等于生产结构修改、合并发布或旧数据回填的执行授权。
