# 个人账单规格：明细、追加退款与逻辑删除

## Problem Statement

LifeSpace 使用者需要在现有工作台中手动记录和回看已经发生的个人收入与支出。目前正式应用没有财务页，无法持久保存本人账单、按日期查找交易或清楚追溯多次退款。

使用者希望每笔实际交易独立保留金额和发生时间，退款不会覆盖原支出；电脑和手机都能方便操作，换设备后仍能读取本人数据。第一版优先保证正常使用，避免为了罕见故障增加复杂交互。

## Solution

在 LifeSpace 的“财务”入口交付个人账单明细页，采用已确认的 A 表格方案，支持新建普通收入或支出、查看详情、日期筛选与分页、为支出追加独立退款流水，以及不可恢复的逻辑删除。

复用现有访问账户、登录和准入白名单，按账单所有者隔离数据。统一使用人民币和北京时间；普通流水创建后不可编辑，录入错误通过删除并重新录入处理。退款独立记为收入，继承父支出的交易账户与分类，原支出金额保持不变，交易状态由有效退款自动推导。

## User Stories

1. 作为获准访问 LifeSpace 的使用者，我希望从现有“财务”入口进入个人账单页，以便在同一工作台管理自己的收支。
2. 作为账单所有者，我希望刷新页面或换设备登录后仍能读取本人流水，以便长期保留实际交易记录。
3. 作为账单所有者，我希望其他访问账户无法读取或操作我的流水，即使知道流水标识也不能访问，以便账单彼此隔离。
4. 作为使用者，我希望在电脑和手机上使用已选定的 A 方案，以便查看、填写和确认操作时保持清晰一致的体验。
5. 作为使用者，我希望每笔普通收入和普通支出都是独立流水，以便分别记录每次实际交易。
6. 作为使用者，我希望新建普通流水时默认支出、时间为打开卡片时的当前北京时间，其他输入为空且分类不预选，以便明确填写本次交易。
7. 作为使用者，我希望输入金额绝对值并由收支方向显示正负号，以便支出保存为负数、收入保存为正数。
8. 作为使用者，我希望每笔流水具有精确到秒的交易时间、金额、交易账户、收支类型、交易状态和交易分类，并可选填备注，以便信息完整。
9. 作为使用者，我希望交易账户暂时自由填写，以便直接使用实际付款或收款账户名称。
10. 作为使用者，我希望普通支出按顺序提供交通、住宿、餐饮、购物、人情支出、充值、订阅、投资理财、其他九个分类，以便统一记录支出用途。
11. 作为使用者，我希望普通收入按顺序提供工资、兼职、投资理财、人情收入、二手转卖、其他收入六个分类，以便统一记录收入来源。
12. 作为使用者，我希望分类固定单选、切换收支方向后重新选择，以便避免保留不适用的分类。
13. 作为使用者，我希望投资买入和赎回分别按实际付款与到账全额记录，以便保留真实资金进出，而不是只记录收益差额。
14. 作为使用者，我希望“充值”用于向其他方充值，其他消费仍由我按实际交易手动记录，以便不被自动跳过或合并规则限制。
15. 作为使用者，我希望允许补录已经发生的交易但禁止未来时间，以便交易时间表达事实。
16. 作为使用者，我希望金额非零、最多两位小数、符号与收支一致，且单笔绝对值不超过 999,999,999.99 元，以便金额合法且精确。
17. 作为使用者，我希望交易账户去除首尾空白后非空且最多 50 个 Unicode 码点，备注去除首尾空白后可空且最多 500 个码点，以便中英文和 emoji 采用一致的输入边界。
18. 作为使用者，我希望输入不合法时说明原因、保留已填内容且不截断文字，以便修正后继续保存。
19. 作为使用者，我希望创建后的原始交易内容不可编辑，以便原交易事实保持稳定，录错时由我删除并重新录入。
20. 作为使用者，我希望查看、新建和登记退款使用居中弹出卡片，删除使用紧凑的二次确认卡片，以便操作层次明确。
21. 作为使用者，我希望取消、关闭、Escape 或点击遮罩直接丢弃新建或退款表单输入，以便无需额外确认或处理草稿。
22. 作为使用者，我希望取消退款或关闭删除确认后回到列表，以便继续查看其他流水。
23. 作为使用者，我希望交易时间数字可直接分段编辑，点击输入框空白、边框或日历图标可打开日历与时分秒浮窗，以便按习惯选择时间。
24. 作为使用者，我希望小时 00–23、分秒 00–59 的滚动、触控和键盘选择都在边界停止，不循环或进位，以便不会意外改变其他时间段。
25. 作为使用者，我希望时间选择滚动稳定后才能确认，确认才更新字段，取消浮窗保留外层表单及原值，以便避免误写时间。
26. 作为使用者，我希望时间浮窗在短屏和手机上完整可用，并禁止确认不合法时间，以便无需退出表单也能完成选择。
27. 作为使用者，我希望从普通支出详情登记一次或多次退款，以便记录每次实际到账。
28. 作为使用者，我希望退款作为独立正金额收入流水显示，能够识别退款身份并打开父流水，以便追溯原交易。
29. 作为使用者，我希望退款自动沿用父支出的交易账户和交易分类且不可修改，以便保持关联一致；即使分类属于支出，也不替换为普通收入分类。
30. 作为使用者，我希望退款时间默认为打开时的当前北京时间，金额和备注为空、不预填剩余额，以便主动填写本次实际退款。
31. 作为使用者，我希望退款时间不早于父支出、不晚于当前时间且允许同秒，以便关联事实符合时间顺序。
32. 作为使用者，我希望只能向本人未删除的普通支出登记退款，以便普通收入、退款和他人流水不能被误用为父流水。
33. 作为使用者，我希望累计未删除退款不能超过原支出金额绝对值，全额退款后停止追加，以便不会超额退款。
34. 作为使用者，我希望原支出金额始终保留，退款只使状态在已完成、部分退款和全部退款之间变化，以便区分原金额和退款进展。
35. 作为使用者，我希望普通收入和退款流水始终显示已完成，以便不会出现不适用的退款状态。
36. 作为使用者，我希望父支出详情能查看关联退款，以便了解每次退款的金额和时间。
37. 作为使用者，我希望列表默认全部时间、按各流水交易时间倒序每页 30 条展示，并在同秒交易间稳定排序，以便不漏不重地浏览更早记录。
38. 作为使用者，我希望列表和详情展示流水信息及退款身份，以便快速判断每笔交易的性质。
39. 作为使用者，我希望按今天、近 7 天、近 1 个月或自定义日期筛选，以便找到所需时期的流水。
40. 作为使用者，我希望所有筛选按北京时间自然日且包含首尾两日，近 1 个月固定为含今天的 30 天，以便不受设备时区或月份长短影响。
41. 作为使用者，我希望自定义范围在独立双日历浮窗中选择，左为开始、右为结束，手机空间不足时上下排列且不遮挡入口，以便清楚指定范围。
42. 作为使用者，我希望“本周”和“本月”只填充日期草稿，分别覆盖周一至周日和月初至月末，以便确认后再应用。
43. 作为使用者，我希望自定义日期只有点击应用才生效，再次点击入口、取消、Escape 或外部点击都丢弃草稿，再开恢复已应用范围，以便保留原筛选。
44. 作为使用者，我希望日期条件改变后回到第一页，以便从完整的新范围开始查看。
45. 作为使用者，我希望支出和退款按各自发生时间参与筛选，退款仍能打开范围外未删除的父流水且不将父流水插入列表，以便日期结果准确。
46. 作为使用者，我希望父支出状态始终依据全部有效退款计算，而不受当前筛选或页码影响，以便状态可信。
47. 作为使用者，我希望新建或退款成功后关闭卡片、回到全部时间第一页，并继续按交易时间排序，以便回到统一列表起点；补录旧交易不强行置顶。
48. 作为使用者，我希望删除成功后保留日期筛选和当前有效页，末页消失时退回上一有效页、无数据时显示第一页空态，以便继续原来的浏览。
49. 作为使用者，我希望刷新或重新进入财务页恢复全部时间第一页，以便每次进入有统一起点。
50. 作为使用者，我希望进入页面、重新聚焦和成功写入后读取最新数据，并能手动刷新数据，且重新聚焦或手动刷新数据不丢弃正在填写的表单，以便兼顾多设备同步和录入。
51. 作为使用者，我希望分页期间其他设备新增或删除时提示列表已更新，保留筛选并回到第一页重读，以便不混合不同版本的列表。
52. 作为使用者，我希望删除前看到交易关键信息和不可恢复提示，以便确认实际要删除的流水。
53. 作为使用者，我希望删除父支出时明确显示关联退款数量和联动影响，确认后一起删除父支出及其退款，以便不留下可见孤立退款。
54. 作为使用者，我希望提交删除时重新核对已展示的具体退款范围，范围变化即更新提示并要求再次确认，即使数量没变也一样，以便只删除我实际确认过的内容。
55. 作为使用者，我希望无关的新建交易不会使原删除确认失效，以便正常操作不受无关变化打断。
56. 作为使用者，我希望单独删除退款时保留父支出及其他退款，并按剩余未删除退款重新计算父状态，以便修正错误退款。
57. 作为使用者，我希望删除后流水从列表、详情、关联读取及退款计算中排除，不能恢复或继续作为父流水，以便删除结果一致。
58. 作为使用者，我希望同一次保存重复点击或当前页面内重试只创建一次，而不同真实交易即使内容完全相同也能各自保存，以便既防重复又不误合并交易。
59. 作为使用者，我希望旧请求重试不会复活已删除流水，重复删除保持成功且不再次改变数据，以便重试安全。
60. 作为使用者，我希望保存结果未知时看到明确提示，并在当前页面沿用原请求编号重试或刷新查看列表，以便判断是否已经保存。
61. 作为使用者，我希望刷新或离开后不恢复旧提交、不自动再次保存，也不持久暂存交易命令，以便提交行为简单可控。
62. 作为使用者，我希望一笔结果未知不阻止其他新建、退款或删除，以便继续正常使用。
63. 作为使用者，我希望保存已经成功但列表读取失败时只重试读取，迟到的成功响应不关闭后来打开的新表单，以便不会重复入账或丢失新输入。
64. 作为使用者，我希望加载中、没有匹配流水、读取失败、保存失败和保存结果未确认分别呈现，以便采取合适的下一步操作。
65. 作为使用者，我希望同时退款不会累计超额，退款与删除竞争不会留下可见孤立退款，失败操作不会只写入部分结果，以便并发时数据仍然一致。
66. 作为使用者，我希望界面保留必要字段、校验与删除影响提示，并精简重复说明，以便专注录入和回看明细。

## Implementation Decisions

- **接入范围**：复用现有 React / TypeScript 网页、Cloudflare Worker、Supabase Auth、准入白名单及同一 Supabase 项目。正式财务页使用 `/finance`，业务接口使用 `/api/ledger` 命名空间；接入现有导航和轻量路由。原型仅作交互依据，不将模拟数据、重置入口、数据状态面板或全量流水调试日志带入正式页面。
- **职责划分**：前端负责输入、即时校验、确认、请求和展示；Worker 每次在线核验身份与准入，从可信身份注入所有者，校验请求与数据库响应；PostgreSQL 在单次事务中完成查重、业务校验、写入、逻辑删除与版本变更。复用现有鉴权请求封装、TanStack Query 和共享 Zod 契约。
- **数据模型**：仅使用 `ledger_entries` 和 `ledger_owner_revision` 两表。前者保存所有者、唯一创建请求编号、原始交易字段、可空父支出关联、创建时间和逻辑删除时间；后者每个账单所有者一行，保存列表版本并提供事务锁。两表共用、按所有者隔离，不新增访问账户体系或交易账户管理表。
- **流水身份与不可变事实**：收支方向只有 `income`、`expense`。收入且存在父支出关联即退款，不增加第三种收支方向、独立退款标记或可编辑状态列。普通流水不关联其他流水；退款父流水须为同一所有者未删除的普通支出，以同 owner 复合外键约束关系。原金额、时间、账户、分类及备注创建后不可编辑。
- **金额和文本**：金额传输、计算和存储使用有符号整数分，数据库使用 `bigint`；绝对值最大 `99,999,999,999` 分，非零且符号与方向一致。输入元金额最多两位小数，不用浮点元金额反复计算。账户与备注 trim 后分别限制为非空 50 个、可空 500 个 Unicode 码点；前端、接口与数据库共同执行边界，不静默截断。
- **固定分类**：共享契约维护稳定代码、中文名及顺序。支出依次为交通 `transport`、住宿 `accommodation`、餐饮 `dining`、购物 `shopping`、人情支出 `gift_expense`、充值 `top_up`、订阅 `subscription`、投资理财 `investment`、其他 `other_expense`；收入依次为工资 `salary`、兼职 `part_time`、投资理财 `investment`、人情收入 `gift_income`、二手转卖 `secondhand_sale`、其他收入 `other_income`。普通分类按方向校验；退款从父支出复制账户和分类，不接受覆盖，也不套用普通收入分类。投资理财记录实际进出全额；不增加充值后消费跳过规则。
- **时间约定**：交易时间精确到秒，接口使用 UTC ISO 8601，数据库使用 `timestamptz`，展示及自然日筛选固定 `Asia/Shanghai`，与首页有效地区和设备时区无关。写入时以服务端时间拒绝未来交易；退款时间不得早于父交易，同秒允许。创建时间由服务端生成，与补录的交易时间分开。
- **退款与状态**：允许同一支出多次退款，未删除退款金额之和不得超过原支出绝对值；账户与分类服务端继承。累计为零时父状态为 `completed`，大于零而未全额为 `partial-refund`，等于原金额为 `full-refund`；全额后不可追加。普通收入和退款固定 `completed`。原支出金额永远保留，状态依据全部有效退款计算，不随筛选和分页改变。新建或删除退款均在同一事务内保证额度与派生结果一致。
- **表单交互**：沿用已确认 A 方案；普通新建默认支出，时间取卡片打开时当前北京时间，其余输入为空。退款账户、分类、收入方向及已完成状态固定，时间同样取打开时刻，金额和备注为空。查看、新建、退款居中弹出；删除使用紧凑确认。表单取消、关闭、Escape、遮罩直接丢弃，不再确认或留草稿；取消退款或删除确认回列表。成功响应仅处理对应的当前表单，避免关闭后来打开的表单。
- **交易时间选择器**：数字保留原生分段编辑，其余输入区域打开独立日历与时分秒浮窗；时、分、秒分别在合法边界停止，不循环、不越界进位。滚动稳定后才允许确认；确认才写回，其他关闭方式丢弃浮窗草稿并保留外层表单。直接输入与浮窗选择执行相同时间校验；空间不足时浮窗居中，短屏调整可见行数，保证控件可用。
- **日期筛选**：默认无日期条件；今天为当日，近 7 天包含今天及前 6 天，近 1 个月为包含今天的 30 天。自定义起始日不得晚于结束日，首尾包含；本周为周一至周日，本月为月初至月末。接口接收 `startDate`、`endDate` 的北京时间日期，服务端转为开始日零点至结束日次日零点的左闭右开区间；全部时间同时省略两者。
- **日期浮窗**：独立双日历，桌面并排、手机必要时上下排列，不推动原页面且不遮挡触发入口。“本周”“本月”只填草稿，点击应用才更新筛选；再次点击自定义、取消、Escape 或外点均关闭并丢弃草稿，再次打开恢复已应用范围。正文以字段、操作和必要反馈为主，保留校验与删除警告。
- **列表与关联详情**：每页固定 30 条，按交易时间和流水标识稳定倒序。父子各按自己交易时间筛选；关联入口可读取日期范围外的本人未删除流水，不将其插入当前结果。单笔详情返回必要退款关联，始终排除已删除或其他所有者记录。
- **分页和刷新**：列表输入 `page`（默认 1）及可选 `version`，响应包含 `items`、`total`、`page`、`pageSize`、`version`。列表、总数、版本及派生状态在同一短事务内持有所有者共享锁读取。分页发现外部写入造成版本变化时，明确提示、保留日期筛选并回第一页重读；切换筛选也回第一页。普通创建不要求携带账户旧版本。成功新建或退款回全部时间第一页，补录不置顶、无额外刚保存入口；本页删除保留筛选和有效页码，末页消失则退回最近有效页。刷新或重新进入恢复默认。进入、重新聚焦、成功写入和手动刷新时取新数据，读取不丢弃正在填写的表单，不引入实时推送。
- **逻辑删除与确认范围**：删除写入删除时间，保留底层记录但不可恢复；所有可见读取、退款额度及父流水选择排除已删除数据。删除父支出同时删除其全部未删除退款，删除单笔退款保留父及其他退款。预览展示关键信息、不可恢复提示、退款数量和联动影响，并生成父流水及全部有效退款标识对应的影响范围；提交在锁内重新核对具体范围。集合变化即停止本次删除，更新提示后再次确认，数量相同而成员不同也视为变化；无关流水变化不触发此确认。
- **事务与索引**：首次写入安全建立所有者版本行；未使用账户查询返回空列表和版本 0。同 owner 写事务持有该行排他锁，先查请求或重复删除，再校验业务、写流水、递增版本并原子提交；不同 owner 不共用该锁。无实际变更不递增版本。锁只覆盖数据库操作，不跨网络等待或用户确认。活跃列表索引按 owner、交易时间倒序、标识倒序，另设活跃退款关联索引。第一版面向个人和少量白名单使用者，以单 owner 累计 10 万条作为索引与分页验证规模，不设为产品条数上限或性能承诺。
- **创建去重**：普通创建和退款分别携带 UUID `requestId`，同次操作在当前页面重试使用原编号。唯一约束覆盖 owner 和请求编号，并包含逻辑删除记录；同编号比较相应不可变输入，相同返回原标识及当前列表版本，不同拒绝复用。退款查重先于父流水当前有效性及可退余额校验；已删除流水旧请求不重建、不返回交易正文。不同编号内容相同允许独立创建。删除已删除目标返回成功，不再次变更或递增版本。不增加回执或操作日志表。
- **异常处理**：提交时防止同次操作重复点击。明确校验失败保留输入；网络异常提示结果未确认，当前页面内保留原请求编号供安全重试，刷新后通过列表查看，不自动重提。不持久保存交易命令、不建设跨刷新恢复队列，不因某笔结果未知限制其他操作。已确认保存成功而重读失败只重试读取。区分加载、空结果、读取失败、保存失败与结果未知，并提供相应重试。
- **权限与安全**：两表开启 RLS，浏览器 `anon`、`authenticated` 不开放业务表或 RPC 权限；Worker 通过现有服务端 PostgREST → PostgreSQL RPC 调用链访问。服务端凭据可绕过 RLS，因此所有受控查询和写入仍显式限定可信 owner，客户端不得指定任意所有者、退款账户、退款分类或状态。API 沿用 `no-store`、稳定错误格式和既有身份错误处理；前端查询缓存按所有者及条件隔离，账户切换沿用既有业务缓存清理，不记录真实账单正文或密钥。

已确认的 HTTP 接口职责如下；实现时在共享契约中固定完整请求、响应与业务错误，保持下述行为约定：

| 接口 | 行为 |
| --- | --- |
| `GET /api/ledger/entries` | 按日期、页码和可选列表版本读取本人未删除流水 |
| `GET /api/ledger/entries/:id` | 查看本人未删除流水及退款关联 |
| `POST /api/ledger/entries` | 携带请求编号创建普通收入或支出，不接收父流水 |
| `POST /api/ledger/entries/:id/refunds` | 携带请求编号创建退款，固定收入并继承父支出账户与分类 |
| `GET /api/ledger/entries/:id/delete-preview` | 返回删除摘要、退款数量与具体影响范围标识 |
| `POST /api/ledger/entries/:id/delete` | 核对已确认影响范围并执行原子逻辑删除 |

JSON 采用 `requestId`、`direction`、`amountCents`、`occurredAt`、`accountName`、`categoryCode`、`note`、`parentEntryId`、`createdAt` 和派生 `status`；普通流水的 `parentEntryId` 为 `null`。不提供修改交易字段的接口。

## Testing Decisions

- **已确认的主要接缝**：正式财务页 → 真实 Worker → 隔离本机 PostgREST / PostgreSQL。沿用现有 Adventure 的真实数据库浏览器支持及临时数据库执行器，扩展加载账单结构。控制测试身份、必要时钟与故障条件，业务请求契约、事务、列表、退款状态及持久结果使用真实实现。使用者已确认此接缝。
- **好测试的标准**：断言用户可见内容、正式 HTTP 行为、必要持久结果与外部副作用；不绑定组件树、私有函数、SQL 文本或动画中间帧。原型内存、模拟 RPC 和跳过的数据库测试不能证明正式功能通过。少量 Worker 契约／权限、数据库约束／并发测试只补充主链路难以稳定表达的边界，不为每层建立独立替身系统。
- **先例与覆盖模块**：复用 Adventure 的页面到真实 Worker／隔离数据库模式、HTTP 跨账户与并发回归、数据库事务及权限探针；沿用现有 Worker 契约和可信身份注入测试，及已有页面在桌面、390px 手机和短屏下的键盘、浮层、刷新回读验证。覆盖账单页、Worker 账单接口和两表事务，不用旧业务模型或原型替代账单实现。

| 场景组 | 关键可观察结果 |
| --- | --- |
| 普通收入与支出 | 独立创建、刷新持久回读、默认值正确；固定分类名称顺序、方向切换清空、非法分类拒绝；投资买入 -1,000 与赎回 +1,050 各自按全额保存 |
| 输入边界 | 金额上限及多一分钱、零金额、超两位小数和符号错误；trim 后账户 50／51、备注 500／501 码点，含中文及 emoji；错误保留输入且不截断；未来时间拒绝 |
| 退款生命周期 | -100 支出后 +30、+70 独立展示，父状态由部分到全部且金额始终 -100；删除 +70、+30 后状态依次恢复；账户与分类继承且不能覆盖，支出分类可合法用于退款收入 |
| 退款限制 | 同秒允许、早于父时间和未来拒绝；本人有效普通支出以外不能作父；全额后多退 0.01 拒绝；并发退款不会超额，父删除与退款竞争无可见孤儿 |
| 日期与分页 | 非北京设备时区仍按北京时间；跨午夜、跨月与首尾包含；近 7 天与 30 天、本周及本月准确；61 条含同秒记录分为 30／30／1，稳定不漏不重；删除不占名额 |
| 筛选与关联 | 9 月支出、10 月退款在 10 月仅列退款；仍能打开未删除父支出，父状态按全部有效退款计算；已删除或他人关联不泄漏 |
| 刷新与页面位置 | 保存后全部时间第一页、补录不置顶；删除保留筛选和有效页、删空末页回退；外部版本变化提示并保留筛选回第一页；重新进入恢复默认，重新聚焦或手动刷新数据不丢表单，迟到响应不关闭新表单 |
| 删除与确认变化 | 父子同事务逻辑删除、单退款删除恢复父状态；预览后新增或移除退款须重新确认；退款 A 换成 B 而数量相同仍重新确认；无关新建不阻止原确认；重复删除不增加版本 |
| 去重与结果未知 | 同编号并发／重试只有一笔，不同内容同编号拒绝；不同编号同内容允许；旧请求不能复活删除流水；退款旧请求在余额或父状态变化后仍正确去重；未知结果不阻止其他操作，刷新不恢复旧提交；已成功后读取失败只重读 |
| 账户与事务边界 | 无账户数据时空列表版本 0；首次并发写入安全建立版本行；数据库事务失败时完整回滚，不留下部分流水或版本变更；他人标识不能用于列表、详情、退款、预览或删除，浏览器角色不能直访表及 RPC，客户端 owner 不能越权 |
| 弹层与输入体验 | 桌面／手机居中卡片和紧凑删除确认；取消、关闭、Escape、遮罩按约定返回与丢弃；日期草稿仅应用生效，再点入口撤销，重新展开恢复已应用范围；交易时间数字直编、浮窗确认、滚动稳定、防未来及退款下界、有限滚轮、键盘／触控边界和短屏可见性 |
| 状态反馈与规模 | 明确区分加载、空态、读取失败、保存失败和结果未知；使用合成 10 万条单 owner 数据检查索引及日期／深页读取，记录实测环境与结果，不将未测指标写成承诺 |

- **验证环境与交付门禁**：数据库套件须显式启动隔离 PostgreSQL／PostgREST；现有默认 CI 不自动启动此环境，不能将跳过计为通过，应提供实际运行证据。测试使用合成数据，不读取或清理生产账单。受控身份测试与真实登录准入验收分别记录。
- **实施验收**：按仓库约定先密钥扫描，再完成相关接口、安全、类型、构建和浏览器检查，完成规范与需求双轴评审。自动检查通过后启动当前功能分支预览、主动打开浏览器供用户验收；随后取得具体 PR 的明确合并确认。合并后核对 Cloudflare 部署与提交 SHA、生产页面及相关只读接口、密钥隔离，部署验收后才关闭 Issue。原型确认不代表正式功能或生产验收通过。

## Out of Scope

- 编辑既有流水、恢复已删除流水、物理删除入口、收支汇总、图表和财务分析。
- 交易账户管理、账户余额、转账与还款分类及业务规则；自定义分类、自动分类和自动跳过或合并消费。
- 导入、导出、多币种、预算、自动记账或外部交易同步等未纳入本期已确认明细流程的能力。
- 后台实时推送、持久提交队列、跨刷新命令暂存与恢复、额外操作回执或日志表，以及由这些机制产生的本地存储故障交互。
- 备份任务、异地存储、保留策略、灾难恢复、数据丢失窗口及恢复目标，不列为本期上线验收项。
- 更换认证或基础设施、改造其他业务页面；本次规格整理本身不包含正式编码、任务拆分、建表、迁移、提交、合并或部署。
