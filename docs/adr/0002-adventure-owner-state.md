# 人生冒险使用账户隔离聚合和版本提交

人生冒险是个人可写任务与成长数据，复用既有 Auth 在线验证身份。旧首页共享 tasks/schedules 不迁移、不改写。

Worker 以 verified identity UUID 访问 Supabase 独立 `adventure_states`；浏览器对该表无直接读写权限。每个账户保存一个 JSON 状态、版本和命令 journal，服务端严格领域命令计算后以 owner_id 和预期 version 条件更新。journal 与奖励来源在同一次 CAS 提交；同 key 重试返回稳定结果和最新状态，普通版本冲突要求刷新确认；读取刷新只读取／初始化并生成投影，不执行周期或延迟结算。

账户规划日期固定 Asia/Shanghai，由服务端时钟决定，与天气地区和客户端日期独立。状态与命令 journal 同次 CAS 提交，初始化不能覆盖已有数据。2026-10-20 目标领域要求在服务端校验特殊独立区、目标归属、聚焦配额、迁移及终态只读，完成历史保存当时归属。目标达成和主线结束不能撤销；本期任务限一次性任务。取消完成后业务记录逻辑删除，用户界面和有效统计排除，数据库记录与 journal 保留且同次 CAS 提交，不物理删除账户状态行。任务完成／目标达成的事实与奖励实时同次 CAS 提交，取消完成及对应任务奖励同时逻辑删除，不追加负数冲正。总经验由有效奖励求和，等级和七个成就按同一版本有效事实实时计算，不单独保存等级、解锁状态或解锁日期；来源奖励与命令 journal 仍持久保留。记录不自动裁剪，不能静默丢失历史。

本期不引入关系表事务 RPC、新存储服务或客户端整包写入。service_role 绕过 RLS，因此强制 owner 条件与在线身份检查不可省略；新表无 auth.users 外键不改变授权规则。


物理表保持现状；本轮 [数据库设计](../adventure/backend-database.md) 定义 schemaVersion=2 的内部事实结构，[业务逻辑](../adventure/backend-business-logic.md) 定义命令、能力和投影。安排与完成记录分别保存，任务身份不因改期改变；内部 JSON 引用约束由后端校验，不能当成 SQL 外键。新 journal 只保存稳定事实回执，不保存等级或成就状态。上述均为设计稿，本次不修改现有 DDL 或持久化代码。
