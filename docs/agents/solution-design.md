# 方案设计规范

状态：2026-11-17，Issue #229 建立。适用于 LifeSpace 的功能设计、技术方案、数据变更和跨模块改造。

本文回答“为什么做、做成什么、边界在哪、如何证明方案可行”。日常分支、评审和交付流程见 [开发与交付](git-workflow.md)；合并、迁移、停流、回滚和生产验收见 [上线与发布门禁标准](release-standards.md)。

## 项目背景

LifeSpace 是个人使用的日常信息工作台，不是面向多租户或大规模并发的 SaaS。当前包含首页、新闻、人生冒险、个人账单和 Token 看板；访问采用 Supabase Auth 与邮箱白名单，业务数据按访问账户隔离。

运行形态：

- 前端为 React/Vite，后端为 Cloudflare Worker，静态资源由 Worker 的 `ASSETS` 绑定提供。
- 持久化主要使用 Supabase Postgres；鉴权使用 Supabase Auth；白名单、星座缓存和 OAuth 状态使用 Cloudflare KV。
- LifeSpace 生产使用一个 Worker 和一条自定义域名路由，`main` 合并后由 Cloudflare Workers Builds 自动构建和部署。
- 没有常设 staging。高风险变更按需申请隔离 Supabase 项目或独立 Worker，普通改动使用本地预览、CI 和隔离测试。
- 数据库迁移不在自动部署中执行，必须单独操作；迁移历史、对象权限和现网版本需要在上线前核对。

这些约束决定了本项目优先选择简单、可观察、可人工恢复的方案。个人项目不等于降低安全要求：账户隔离、鉴权、密钥保护、输入校验和不可逆数据保护仍然必须成立。

## 核心原则

### 个人项目复杂度原则

默认接受短时停机、停流、回滚上一版、关闭入口和人工重试。能用这些运维手段在可接受时间内解决的问题，不新增兼容层、双写、自动回滚编排、常驻特性开关、长期多版本适配等防御性代码。

判断“过度防御”时看当前是否存在真实需求，而不是假想规模：

- 不存在的旧客户端、旧数据形态或并发规模，不为它们预先设计迁移分支。
- 一次性迁移能用停流完成时，不增加双写和在线回填。
- 单人维护的系统能用人工确认和上一版回滚解决时，不增加自动编排和复杂状态机。
- 没有明确产品需求时，不为“以后可能要用”增加通用抽象。

以下能力不属于过度防御，仍按实际风险保留：

- 鉴权、权限、账户隔离、输入校验和敏感信息脱敏。
- 防止重复提交、重复发奖或重复写入的幂等约束。
- 破坏性数据变更前的可恢复备份和恢复演练。
- 关键失败路径的错误提示、日志和可观察性。
- 对真实存在的旧客户端、旧回执或历史数据的兼容处理。

### 停机优先

当停机、停流或关闭入口能在可接受时间内消除风险时，优先选择运维手段，而不是增加运行时复杂度。

采用停机方案前必须回答：

1. 停哪些入口：主域名、`workers.dev`、预览地址、直连 RPC、后台任务、采集器上传和管理通道。
2. 如何确认写入已停止：在途请求是否排空，旧 Worker 是否还能写，重试和队列是否会补写。
3. 停机窗口多长，是否可接受，失败时如何保持停机而不是带病恢复。
4. 回退点是什么：上一版 Worker、上一版数据、关闭功能，还是只做前向修复。
5. 恢复条件是什么：哪些探针、页面、接口或数据对账必须通过。

停机不是“先停再说”。所有入口、在途请求、恢复条件和证据都要在操作前写清楚。

### 可逆与可证明

- 优先选择容易回退、影响面小、能人工核对的方案。
- 不可逆的数据变更必须单独说明，不把“迁移脚本里有定义”当作回滚备份。
- 方案中的“已验证”必须说明验证层级：本地测试、CI、隔离环境、用户验收还是生产验收。
- 没有验证的条件写成假设或未验证项，不写成结论。

### 优先复用成熟模块

优先选择现成、成熟、维护活跃的模块作为方案子模块，避免重复实现通用能力。自己写只应在以下情况成立：

- 现成模块不满足已确认的需求或数据语义。
- 模块的许可证、安全边界或运行环境不合适。
- 集成成本明显高于实现和维护一个窄功能。
- 模块已停止维护，或无法固定版本、审计行为和验证输出。

优先顺序：

1. 使用项目已有依赖或共享模块。
2. 使用成熟的上游库、CLI 或平台能力。
3. 在现有模块外写一层窄适配或校验。
4. 最后才自建通用能力，并在方案中说明原因。

采用外部模块前至少核对：

- 版本固定方式和依赖锁定，不使用浮动 `latest`。
- 许可证是否允许当前用途。
- 维护状态、发布节奏和已知安全问题。
- 输入输出契约、失败行为和可观察性。
- 是否把凭据、用户数据或敏感日志带到不该去的地方。
- 出问题时能否替换、降级或退回自建窄实现。

模块只承担它擅长的部分，项目负责边界、校验和业务语义。不要因为引入模块就把整个业务流程交给它，也不要在模块外重复实现同一套解析或计算。

**项目范例：Token 采集复用 Tokscale。** `@tokscale/cli@4.23.0` 独占来源解析、继承／fork／归档去重、模型和 token／价格统计；采集器只负责固定版本调用、时区与输出结构校验、联合分项对账、未知值保留和上报，见 [ADR 0020](../adr/0020-token-recorded-usage-authority.md) 与 [统计契约](../token-usage-contract.md)。这比自建日志解析和价格引擎更简单，也保留了明确的替换边界。

## 何时需要方案设计

不是每个改动都需要完整设计文档。按影响选择最小够用的记录：

| 改动 | 最低记录 |
|---|---|
| 文案、局部样式、明确的小 bug | Issue 中写目标、范围和验证方式即可 |
| 单模块功能、少量接口或页面调整 | Issue 中写现状、方案、边界、失败处理和验证 |
| 跨模块改造、新外部依赖、公开接口契约、鉴权或权限变化 | 独立方案说明，列出选项、取舍和兼容性 |
| 持久化结构、不可逆数据操作、整体架构变化，或会改变迁移／回退策略的迁移 | 方案说明加 ADR；涉及生产操作时另写发布计划 |

以下情况必须先讨论方案，再进入实现：

- 需要改变核心业务规则、数据模型或状态流转。
- 需要改变鉴权、权限、白名单或密钥边界。
- 需要改变公开接口契约或已有客户端行为。
- 需要迁移、回填、删除或重写既有数据。
- 需要引入新的外部服务、付费资源或长期运维负担。
- 影响范围或关键行为无法核实。

## 方案设计内容

### 1. 问题与目标

说明：

- 谁遇到什么问题，当前行为是什么。
- 本次要改变什么，不改变什么。
- 成功标准是什么，如何观察。
- 明确的非目标，防止实施范围扩大。

如果需求本身有影响结果的歧义，先向用户确认，不把猜测写进方案。

### 2. 现状与约束

开始设计前阅读相关代码、`CONTEXT.md`、对应 ADR、现有规格和验收记录。至少核对：

- 当前数据结构和写入路径。
- 当前鉴权、权限和账户隔离方式。
- 当前部署、配置和外部依赖。
- 已有失败记录和未解决问题。
- 现有方案中哪些决定仍然有效，哪些已被取代。

新方案与已有 ADR 冲突时，明确指出冲突并重新讨论，不静默覆盖。

### 3. 方案选项与取舍

对有实际影响的改动，至少比较两个可行方案；小改动可以只记录“为什么采用当前做法”。

比较维度：

- 实现和运维复杂度。
- 是否有成熟模块可直接复用，复用后的集成和替换成本。
- 对现有用户、数据和接口的影响。
- 失败时的表现和恢复方式。
- 是否需要停机、迁移或额外资源。
- 可验证性和证据成本。
- 是否引入长期维护负担。

“保持现状”也是选项。不要只列一个方案再补理由。

### 4. 契约与边界

按实际需要说明：

- 输入、输出、错误语义和幂等要求。
- 数据模型、所有权、唯一约束和生命周期。
- 鉴权、权限、RLS 和账户隔离。
- 前后端版本兼容关系。
- 外部依赖的超时、失败、缓存和降级。
- 日志、监控和敏感信息边界。

契约要写到可以实现和验证的程度，不把关键行为留在“实现时再看”。

### 5. 数据与迁移

迁移分类、备份边界和停流要求以 [上线与发布门禁标准](release-standards.md#迁移分类)为唯一权威来源。方案设计阶段必须判断迁移属于纯新增、原位修改还是破坏性变更，并记录判断依据；不能证明是纯新增时，按原位修改处理。

纯新增也要核对名称冲突、权限范围、扩展依赖和迁移历史。既有表加索引、修改既有函数或权限，均按原位修改处理。

迁移方案必须说明：

- 迁移顺序和依赖。
- 是否单事务，事务边界在哪里。
- 传输上限和完整脚本大小。
- 失败时是回滚、前向修复还是保持停机。
- 迁移历史是否有且仅有一条对应本次脚本的记录，实际平台版本是什么。

### 6. 失败模式与恢复

至少列出：

- 请求失败、超时和结果未知。
- 重复请求、重复写入或重复发奖。
- 部分成功和前后端版本不一致。
- 外部依赖不可用。
- 迁移中断、权限错误或数据不一致。
- 回滚失败或恢复备份覆盖新事实。

对每个失败模式说明用户看到什么、系统保留什么、如何重试、是否需要人工处理。不要用“不会失败”代替失败设计。

### 7. 验证与证据

方案要说明用什么证明，而不是只写“测试通过”：

| 证据 | 能证明什么 |
|---|---|
| 已由用户确认的原型 | 可用于确认需求、流程和交互意图 |
| Agent 自验 | 本地实现和受影响路径已实际检查 |
| 单元／接口测试 | 计算、契约和错误分支 |
| 隔离数据库测试 | 迁移、事务、权限和真实查询 |
| 浏览器测试 | 页面可访问和关键交互 |
| 构建与类型检查 | 代码可构建、类型一致 |
| CI `validate` | 固定提交通过仓库门禁 |
| 用户验收 | 用户确认需求和交互 |
| 生产验收 | 线上版本、接口、权限和数据符合预期 |

不同层级不能互相替代。模拟数据、内存原型和本地预览不能证明生产链路。

### 8. 决策记录

以下情况写 ADR：

- 决定整体架构、持久化结构或核心数据语义。
- 决定鉴权、权限、密钥或公开接口边界。
- 决定不可逆操作、迁移策略或回退方式。
- 方案会长期约束后续实现，或取代已有 ADR。

ADR 记录决定、理由、被放弃的选项和后果。Issue 记录本次范围、进度和证据；`CONTEXT.md` 只记录稳定的领域术语，不承载临时方案。

## 方案评审

实现前按影响评审方案。这里的“自检”只指实现前的方案评审，不替代开发后的适当检查、双轴评审、必需 CI 和发布验收：

- 低风险改动：作者自检方案，Issue 写清目标和验证即可；开发后仍按 [开发与交付](git-workflow.md)执行检查、评审和发布验收。
- 跨模块或需确认的改动：至少一次独立评审，检查需求、边界、失败模式和回退。
- 涉及生产迁移或不可逆数据：方案、发布计划和回退路径分别确认。

评审问题要闭环。范围变化后更新方案和验收依据，不沿用旧结论覆盖新范围。

## 界面相关方案

界面视觉、响应式、可访问性和截图验收不在本规范展开，后续另立 Issue。界面方案合并前的页面检查、桌面／手机视口和用户验收按 [开发与交付](git-workflow.md#界面验收)执行。涉及界面的方案只需说明用户流程、关键状态和影响范围。

`DESIGN.md` 只规范正式 Token 路由，不是全站设计系统。其他页面不得把它当作重新设计授权。

## 完成定义

方案设计完成需要同时满足：

- 问题、目标、非目标和范围清楚。
- 关键约束、现有决定和冲突已核对。
- 有实际影响的改动比较过方案和取舍。
- 契约、数据、失败模式和回退边界可实现、可验证。
- 验证层级和未验证项已记录。
- 需要 ADR 的决定已记录。
- 评审问题已闭环，或明确列为阻塞。

## 禁止事项

- 为不存在的规模、客户端或故障预先增加复杂防御代码。
- 用“以后可能需要”作为引入通用抽象的理由。
- 在成熟模块可用且合适时，重复实现解析、计价、鉴权、表单、日期等通用能力。
- 引入外部模块但不固定版本、不核对许可证、不定义失败和替换边界。
- 只写一个方案，不说明为什么放弃其他做法。
- 把迁移脚本、类型检查或 CI 成功当作数据可恢复或生产已验收。
- 用模拟数据、内存原型或本地预览证明真实链路。
- 未经授权扩大方案范围或修改已确认的产品行为。
- 在方案、Issue、日志或截图中暴露真实凭据、白名单或敏感业务数据。
