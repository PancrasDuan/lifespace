# 开发与交付

## 开始任务与创建分支

主目录保留 `main`，作为查阅和同步入口；每个开发任务固定使用一个短期功能分支、一个 Orca worktree 和该工作区中的主 session。

1. 读取对应 Issue 的正文、标签、评论与依赖，查找已有分支、PR、Orca 工作区及其主 session。继续已有任务时复用原工作区和主 session；仅在归属不清时向用户确认。
2. 新任务先成功执行 `git fetch origin`，再从更新后的 `origin/main` 创建分支。同步失败时说明阻塞，不将本地旧引用当作最新基线。AI 分支命名为 `codex/<issue>-<name>`，人工可使用 `feature/<issue>-<name>`。
3. 使用 `orca-cli` 创建和管理工作区，先按技能读取当前版本指南。独立任务显式选择 `origin/main` 为 Git 基线，并用 `--no-parent` 建立独立工作区；Orca 的父子关系不决定 Git 基线。核对创建结果中的实际路径、分支和起始提交，名称冲突时先查重再继续。
4. 等待已有 Orca setup 完成，确认当前工作区的依赖安装、Git 钩子和所需本地配置就绪；配置缺失或 setup 失败时先解决相应问题。依赖、构建产物与运行缓存保存在各自工作区。
5. 工作区就绪后，按“任务交接”将当前任务交给该工作区的主 session。由接手会话在开始修改前核对状态，向用户说明 Issue、工作区路径、分支与起始提交，再进入开发。

## 任务交接

创建 worktree 后，默认将当前任务完整交接至该 worktree 下的 session，并以确认提示送达作为交接完成条件。

1. 优先复用目标工作区中明确负责该 Issue 的 session；需要新会话时，通过 `orca-cli` 在该工作区启动 Codex，用户指定其他 Agent 时遵从其选择。也可在创建 worktree 时一并启动会话并传入交接提示；接手会话需等待 setup 完成后再开始修改。
2. 交接提示包含 Issue、用户目标、已确认范围、交付分级及依据、已有授权及待确认事项、工作区路径、分支与起始提交、现有修改和验证结果、运行中的服务与端口、适用约定的阅读入口，以及下一步。保留尚未完成的确认，不将建议当作用户授权；凭据只引用配置位置，不传递其值。
3. 核对目标 worktree、会话或 Agent 句柄与送达回执。新启动会话以 `prompt.outcome` 为 `journaled` 或 `handed-to-terminal` 确认送达；向已有会话发送时，以 `accepted: true` 确认输入已接受。句柄和字段按当前版本 `orca-cli` 指南解释，发送成功不代表任务已完成。
4. 确认交接完成后，向用户报告目标工作区、分支、会话标识和送达结果；后续澄清、实现、验证和交付由接手会话继续。原会话停止推进该任务，不等待接手会话完成，也不并行继续实现。
5. 启动失败或送达状态不明时，原会话只负责恢复交接并报告实际阻塞。先检查已有会话与操作回执，按 `orca-cli` 指南使用原操作标识重试，避免重复启动会话或重复发送任务。

## 切换任务与并行开发

- 切换任务时恢复目标工作区的主 session，并核对路径、分支和 Issue；保留原工作区的未提交修改、终端和预览服务。任务切换不自动执行 stash、reset 或清理文件。
- 不同任务使用不同分支和工作区。同一工作区同一时间只有一个开发者或 Agent 写入；需要并行实现同一需求时，先明确子任务边界和集成关系，再分别建立分支与工作区。
- 独立任务从 `origin/main` 开始；依赖任务默认等待前置变更合并到 main。用户已明确需要基于其他功能分支开发时，记录依赖分支、起始提交和 PR 目标分支；前置任务合并后重新核对基线和 PR 差异。
- 同时运行的开发预览和浏览器测试使用各自空闲端口，分别通过开发命令的端口参数和 `PLAYWRIGHT_PORT` 指定。核对服务所属工作区后再复用；端口冲突时更换端口，避免停止其他任务的进程。
- 每个任务保留自己的验证记录和预览地址，跨工作区执行命令时显式指定目标目录。

## 交付分级与授权

按实际行为和影响范围判断风险，不以改动行数或文件数量决定是否需要用户确认。

| 分级 | 判断依据与示例 | 交付授权 |
|---|---|---|
| 低风险小改动 | 范围明确、容易回退、关键行为可验证，且不涉及下列重要变更。例如文案与文档修正、局部排版和样式调整、响应式问题，以及恢复已明确预期行为的小 bug 修复 | 用户已给予持续授权；完成检查、评审和变更记录后，直接合并并跟进自动上线，无需逐次请求用户验收或合并确认 |
| 需确认的变更 | 涉及核心业务规则、整体架构、持久化数据结构或迁移、鉴权与权限、密钥、公开接口契约、生产部署配置，或影响范围与关键行为无法核实。例如账单金额与退款规则、任务奖励和状态流转的调整 | 完成实现、验证和评审后，取得用户针对具体变更范围或 PR 的明确合并发布授权，再交付 |

- 开始实现前将分级及依据写入 Issue，评审时复核。实施中触及重要变更或发现影响扩大时，更新分级和记录，在合并上线前解决相应验收与授权事项；同一 PR 包含两类改动时按需确认的变更处理。
- 已有明确授权覆盖当前变更范围时直接沿用，交接会话同样继承，不重复询问。用户对某次任务提出的亲自验收、暂不上线等要求优先执行。
- 两类变更均通过功能分支和 PR 交付，执行密钥扫描、适当检查、双轴评审、必需 CI 与发布验收。

## 安全与验证

1. 新克隆先执行 `npm run setup:git`，启用仓库提交钩子。提交前先查看暂存范围并扫描密钥，真实凭据只放在忽略的本地配置或 Worker runtime secrets。
2. 提交钩子扫描暂存修改；`npm run check:secrets` 扫描全部本地可达历史及当前 Git 文件。固定版本的 Gitleaks 从官方发布下载，校验 SHA-256，输出脱敏。
3. PR CI 的 `validate` 先扫描密钥，再运行接口测试、安全回归、类型检查、构建和浏览器回归。CI 不注入业务密钥，不上传测试轨迹或构建产物。
4. 每次提交和评审重点检查密钥、敏感日志、前端资源和公开响应。扫描命中必须解决；仅允许为已核实的具体假值或误报添加窄范围规则，不可整体豁免文件或测试目录。

GitHub 已启用原生 secret scanning 与 push protection，作为已支持密钥格式的补充。

本地钩子可能未安装或被绕过；main 的必需 CI 是服务端门禁。扫描降低风险，不能证明没有任何敏感信息。

## 开发后评审

1. 在任务工作区完成与改动相称的检查，将本次交付整理为已提交版本，核对 PR 的源分支、目标分支及关联 Issue。未提交内容需要单独说明，不计入该提交的评审结论。
2. 固定评审范围：记录目标分支的提交 SHA、与待审提交的 merge-base SHA，以及待审 HEAD SHA；常规 PR 以 `main` 为目标，本地评审使用已同步的 `origin/main`。用固定 SHA 比较差异，避免评审期间分支移动改变范围。
3. 使用 `code-review` 完成规范与需求双轴评审，分别给出结论，并复核交付分级；报告注明 Issue、比较范围、分级依据、检查结果、发现的问题和未验证项。缺少需求依据时明确说明需求轴无法完成。
4. 修复后检查相对上次待审提交的新增差异，对受影响的规范、需求和测试补充验证，并将记录更新到新 HEAD SHA。同步 main、处理冲突或调整需求后，同样重新核对评审范围；旧结论只覆盖原提交。
5. 本次交付的评审问题解决且验证记录对应最终提交后，按“交付分级与授权”完成相应验收和合并流程。

## PR 与合并

- 开发、测试和评审在任务工作区的功能分支完成，通过 PR 交付。PR 关联 Issue，但不使用自动关闭关键词，部署验收后再关闭 Issue。
- 合并要求最终提交的 `validate` 全部通过、分支包含最新 main、评审问题和讨论已解决。使用 squash merge，合并后可删除远端功能分支，本地工作区与分支按任务收尾流程清理。
- 单人加 AI 模式下，GitHub 必需审批数量为 0；合并发布授权按“交付分级与授权”执行，同一账号的 AI 评审不充当需用户确认变更的人工授权。
- `main` 是生产分支，保护适用于管理员，禁止直接推送、强推、删除与绕过检查。变更保护规则需用户明确授权。

## 界面验收

- 涉及网页功能或交互的变更，合并前启动或复用任务分支的本地预览，核对页面可访问且包含本次变更。默认使用本地预览，外部预览需已有授权。
- 低风险小改动由 Agent 自行检查受影响页面、交互及适用的桌面／手机视口，记录浏览器检查、回归测试或截图结果，完成后直接交付。关键行为无法验证时按需确认的变更处理。
- 需确认的界面变更，自动检查通过后主动打开浏览器供用户验收；提供可点击的预览地址、当前分支和关键验收操作，验收期间保持服务运行。
- 定位、系统权限等依赖真实浏览器环境的行为变化，需在用户常用的系统浏览器验收；内置浏览器中的回退结果不能代替真实能力验收。
- 需用户验收时，验收通过后按交付分级核对已有合并发布授权；仍缺少授权时再请求确认。收到问题时继续修复并重新验证。
- 预览启动或打开失败时记录实际阻塞及其对验证的影响；关键验证未完成时先解决或交由用户验收。分别记录 Agent 自验和用户验收的实际状态。

## 发布验收

main 合并后由 Cloudflare Workers Builds 自动发布；生产分支为 main。非生产分支可通过受限测试账号的候选版本 URL 预览，配置与共享数据库隔离约定见 `docs/database-preview.md`；预览上传不分配正式流量，也不构成合并发布授权。GitHub CI 负责合并门禁，Cloudflare 构建负责部署。

确认 Cloudflare 部署成功且提交 SHA 对应本次合并，核验生产页面、相关只读接口与密钥隔离，再关闭 Issue。部署失败时保持 Issue 开放，通过新分支和 PR 修复；紧急生产回滚需用户明确授权。

## 变更与发布记录

每次交付以 PR 集中保存变更和验证证据，Issue 记录进展、交付分级和最终 PR 链接。

1. 合并前在 PR 记录变更原因、修改前后的行为与影响范围、交付分级及依据、验证结果与未验证项，以及回退方式；需用户确认的变更同时记录已有授权覆盖的范围。
2. 发布后补充发布时间、合并提交 SHA、生产构建或版本标识、部署与线上验收结果；失败、修复或回退情况继续记录到关联 Issue／PR，未完成发布验收时保持 Issue 开放。
3. 交付完成后主动向用户简述变更、验证、PR 和上线结果；低风险改动也执行该汇报。

## 任务收尾

- PR 合并且发布验收完成后，核对任务工作区中的已跟踪修改、未跟踪文件、终端和 Agent 状态，确认没有待保存内容或仍在使用的服务，再通过 Orca 的清理流程移除工作区及本地分支。
- squash merge 的交付归属以 PR 已合并状态和合并提交为依据，不能只用本地分支是否为 main 的祖先判断。存在未保存工作或活跃进程时先处理，不强制删除。
