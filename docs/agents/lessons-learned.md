# 踩坑记录与防范

本文件记录项目中已发生的问题，以及后续 Agent 必须执行的防范措施。每次开始任务先阅读；任务执行、交接、评审和验收时应用相关条目。用户的明确指令优先于本文。

## 已确认原型被简化，修改范围被扩大

### 发生了什么

人生冒险 #164 已确认原型 C：只调整原“主线与目标”页签中的目标栏及相关目标操作，并参考原型实现关系卡。原型截图同时包含整页标题、上方新建区域、经验概览和导航；这些外围区域并未授权重新设计。

拆分出的 #171、#172 主要保留了字段、功能和交互清单，没有将具体原型素材、作用范围及视觉对照写成明确的交接与验收条件。原型素材当时在原工作区且未被跟踪，实施和评审工作区没有固定、可核对的视觉基准。首次实现的功能测试和 CI 通过，但目标栏和关系卡的视觉与原型存在明显差异，仍被交给用户验收。

用户指出差异后，协调者又把原型中的示意页头当成修改依据，要求调整标题、新建区域、经验概览和手机导航，扩大了已确认范围。测试通过和模拟预览可用都不能证明视觉符合原型或改动范围正确。

### 防范要求

1. **确认依据与范围。** 拆票或开始界面任务前，读取上游需求、用户确认的原型和后续纠正，记录原型版本、适用区域、交互要求和明确不变的外围区域。区分原型的产品设计与演示工具栏、示例数据等展示材料。若范围有影响结果的歧义，先向用户确认。
2. **固定并交接原型。** 在任务或 Issue 中引用可访问、可追溯的原型说明及对应桌面、手机和关键状态截图，记录版本或内容摘要；让每个实施、评审工作区确认可以读取同一份材料。原型位于未提交工作区时保留用户改动，不擅自提交或覆盖；按已有授权采用可追溯的交接方式。无法取得已确认原型时，标明阻塞，不凭功能清单猜测视觉。
3. **让每张票继承完整约束。** 界面实施票分别写明功能、视觉依据、作用范围和不应变化的区域；跨票集成验收也引用相同基准。父 Issue 或聊天记录中的用户决策不能只被压缩成字段清单。变更范围或原型有新指示时，同步给受影响的实施者、评审者和验收记录。
4. **同时验证还原与边界。** 在相同桌面和手机视口下，对照原型和最终实现的截图，检查布局层级、组件样式、关键状态和交互；同时对照修改前后页面，检查范围外的页头、导航、共享组件及其他页面未被意外改动。数据或平台限制造成的差异须逐项记录，不能用测试通过或字段齐全代替视觉对照。
5. **评审问题要闭环。** 独立评审依据固定提交分别核对需求、规范和范围。发现原型不符或范围外改动时，记录证据、交实施者处理并复审受影响差异；不通过修改测试预期来掩盖未经授权的布局变化。用户纠正范围时，及时调整受影响的交接与验收基准并按新指示继续；用户明确要求暂停时，停止对应实施。
6. **如实交付。** 在提交用户验收前，记录实际版本、原型对照、范围外检查、自动测试、未解决问题及尚未进行的验证。功能测试、CI、Agent 自验和用户验收分别报告；任一适用门槛未完成时，不称已满足需求或可验收。

## 长 SQL 迁移必须先验证传输上限并确定分段边界

### 发生了什么

人生冒险目标分类迁移脚本 95KB。Supabase `apply_migration` 单次传输有长度限制，执行时被拆成「结构变更」和「函数定义」两段。第一段成功后返回 `success`，数据库结构已变成四表，但 19 个 adventure 函数仍引用已被删除的 `adventure_mainlines`。

这段时间数据库处于「结构已迁移、函数全部失效」的不一致状态。后续又因分段遗漏 `adventure_task_check`，需要额外一次修复。最终迁移历史留下 8 条分步记录，而项目期望的是单条 `20261111000000_goal_categories`。

流量当时已停止，未造成实际数据损失，但在生产迁移中这是不可接受的中间态。

**防范要求**

1. **确认传输上限与分段边界。** 执行长 SQL 前先确认工具的传输上限，并在发送前确定分段边界与每段的完整性（不切断函数体、不切断事务块）。
2. **每段执行后立即验证对象可用性。** 确认函数存在、签名正确、无残留旧引用，再进入下一段。
3. **审慎评估分段带来的迁移历史不一致。** 分段会导致迁移历史与项目脚本版本不一致，须在执行前评估并记录，不得事后以「结果正确」合理化。
4. **优先选择能一次执行完整脚本的通道。** 分段是最后手段。

## 备份方案要先确认工具能力，并区分「数据备份」与「可完整恢复的备份」

### 发生了什么

迁移前的备份过程反复尝试了 `pg_dump`、REST API、`information_schema`、GraphQL、`pip install` 等多种路径，全部失败后才改用 Supabase 插件。这段排查消耗了大量时间，期间用户多次询问是否卡住。

最终只导出了五张表的数据（JSONL + SHA-256），未能取得函数、RLS、索引、约束的完整定义，因为系统表通过 REST 不可访问。严格来说这份备份只能恢复数据，无法原样重建数据库。当时用「迁移脚本里已包含所有函数定义」作为理由，但那属于前向迁移路径，不构成回滚备份。

**防范要求**

1. **动手前先确认可用工具及其能力边界。** 不靠逐个试错消耗时间。
2. **明确备份覆盖范围。** 数据、schema 定义、权限/RLS、索引约束、迁移历史。
3. **schema 定义不完整时说明缺口。** 不得称其为完整备份，应给出补足方式（例如取得数据库连接串后用 `pg_dump`，或通过 Management API 导出）。
4. **备份完成后验证可恢复性。** 不只校验文件存在与哈希。

## 多阶段上线要在开始前写下阶段门禁

### 发生了什么

本次上线实际包含：数据库迁移 → 合并 PR → 自动部署 → 部署核验 → 恢复流量 → 收尾。各阶段之间存在严格依赖（新库与旧 Worker 不兼容，必须先部署新版本再恢复流量）。

但阶段划分和门禁是在推进过程中逐步形成的，由用户在对话中推动，而不是在开工前就有一份清单逐项确认。阶段之间缺少明确的前置条件记录，增加了遗漏风险。

**防范要求**

1. **涉及数据结构切换或前后端不兼容的上线，开始前先写下阶段清单与每阶段门禁。**
2. **每个阶段完成后记录证据。** 命令输出、状态查询结果、部署版本号等，确认后再进入下一阶段。
3. **明确各阶段的可回退点与回退方式。** 尤其是不可逆的数据库变更之后。

## 适用范围说明

以上三条经验源于本次 LifeSpace 人生冒险上线，但描述的风险模式跨平台通用，适用时需注意：

- 长 SQL 分段迁移、备份完整性、分阶段上线门禁在所有涉及外部数据平台（Supabase 及其他具有类似迁移/备份 API 限制的平台）的上线中同样存在；具体工具的传输上限与备份能力边界需在每次上线前核实，不可照搬本项目经验。
