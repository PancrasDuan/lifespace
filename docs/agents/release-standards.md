# 上线与发布门禁标准

状态：2026-11-17，Issue #229 建立。适用于 LifeSpace 的功能合并、生产发布、数据库迁移、停机停流和回滚。

本文回答“什么时候可以合并、什么时候可以部署、什么时候可以迁移、什么时候可以恢复流量，以及什么时候可以关闭任务”。方案取舍和设计边界见 [方案设计规范](solution-design.md)；日常分支、交接、评审和收尾流程见 [开发与交付](git-workflow.md)。

## 适用范围与优先级

适用于：

- 合并到 `main` 并触发 Cloudflare Workers Builds 的代码或配置变更。
- 需要执行数据库迁移、修改外部资源、切换流量或回退生产版本的变更。
- 涉及鉴权、权限、密钥、公开接口、持久化数据或生产部署配置的变更。

要求冲突时按以下顺序处理：

1. 用户最新的明确指令。
2. 当前 Issue、ADR 和具体发布方案中的决定。
3. [开发与交付](git-workflow.md)中的交付分级与流程。
4. 本文的默认门禁。

任何阶段都不能用“测试通过”“构建成功”或“页面能打开”替代尚未完成的生产验收。用户明确暂停或要求暂不上线时，停止对应发布。

## 项目运行形态

- LifeSpace 生产使用一个 Worker `lifespace` 和一条自定义域名路由 `lifespace.onepeace.cc.cd`；静态资源由同一 Worker 的 `ASSETS` 绑定提供。
- `main` 是生产分支。合并后 GitHub CI 与 Cloudflare Workers Builds 都会被触发；GitHub CI 的 `validate` 是合并门禁，Workers Builds 的 `build:ci` 是部署构建，两者是独立链路，不能假设部署会等待 GitHub CI 完成。
- 数据库迁移不在自动部署中执行，必须单独操作。合并、迁移和部署的先后顺序必须按兼容性明确选择。
- 默认没有 staging。普通改动使用本地预览、隔离测试和 CI；涉及生产数据、权限或不可逆操作时，按需申请隔离 Supabase 项目或独立 Worker。
- 生产不是测试库。合成测试必须使用明确的测试身份和合成数据，并在结束后精确清理。

## 核心原则

### 个人项目复杂度原则

默认接受短时停机、停流、回滚上一版、关闭入口和人工重试。能用这些运维手段在可接受时间内解决的问题，不新增兼容层、双写、自动回滚编排、常驻特性开关、长期多版本适配等防御性代码。

具体判断：

- 一次性迁移能用停流完成时，不增加双写和在线回填。
- 单人维护的系统能用人工确认和上一版回滚解决时，不增加自动编排和复杂状态机。
- 没有真实旧客户端或旧数据形态时，不为假想兼容增加分支。
- 真实存在的前后不兼容、旧回执、旧客户端或数据保全需求，仍按实际风险处理。

安全、隐私、账户隔离、密钥保护和不可逆数据保护不因个人项目原则降级。鉴权、权限、输入校验、幂等约束、敏感信息脱敏和破坏性变更前的可恢复备份仍然必须成立。

### 优先复用成熟模块

优先使用现成、成熟、维护活跃的模块承担通用能力，不重复实现解析、计价、鉴权、表单、日期等已有可靠实现。引入外部模块时固定版本、核对许可证和维护状态，并明确输入输出契约、失败行为、敏感数据边界及替换或降级方式。模块只承担它擅长的部分，业务校验、权限和错误语义仍由本项目负责。

### 停机优先

当停机、停流或关闭入口能在可接受时间内消除风险时，优先选择运维手段，而不是增加运行时复杂度。停机方案必须闭环，不能只停主域名而留下其他写入口。

### 不以自动化代替判断

CI、构建、部署状态和探针只能证明对应层级的结果。自动检查通过不等于生产已验收；部署成功不等于数据迁移正确；页面可打开不等于写链路和权限边界正常。

## 交付分级与授权

按 [开发与交付](git-workflow.md#交付分级与授权)判断：

- **低风险小改动**：范围明确、容易回退、关键行为可验证，且不涉及重要变更。完成检查、评审和记录后，按已有持续授权合并并跟进自动上线。
- **需确认的变更**：涉及核心业务规则、整体架构、持久化结构或迁移、鉴权与权限、密钥、公开接口契约、生产部署配置，或影响范围无法核实。必须取得用户针对具体变更范围或 PR 的明确合并发布授权。

同一 PR 同时包含两类改动时，按需确认的变更处理。已有授权必须明确覆盖当前变更；不能把“可以做本地实现”理解为“可以合并或发布”。

## 发布前计划

### 简单发布

不涉及数据库迁移、不可逆数据变化、流量切换或前后端不兼容时，至少记录：

- 变更范围和用户可见行为。
- 交付分级及授权依据。
- 回退方式：回退提交、恢复上一版 Worker，或关闭对应功能。
- 按影响适用的自动检查、验收和生产核验项。
- 生产验证所需但不涉及真实敏感数据的检查。

### 复杂或不可逆发布

涉及数据结构切换、迁移、外部资源删除、前后端不兼容、停机停流或多阶段切换时，必须在开始生产操作前写下阶段计划。至少包含：

| 字段 | 要求 |
|---|---|
| 阶段 | 按依赖排序，说明每阶段做什么 |
| 进入门禁 | 前一阶段哪些证据必须通过 |
| 操作 | 命令、配置位置或受控操作入口 |
| 证据 | 命令输出、版本号、SHA、对象查询或其他可追溯证据 |
| 失败处理 | 停止、前向修复或回退 |
| 回退点 | 可回退到哪个版本或状态 |
| 授权 | 当前阶段是否已被用户明确批准 |

计划写入 Issue 或 PR 后再开始。不得在执行过程中临时补出关键阶段，也不得把“已经做到这一步”当作继续操作的授权。

## 环境与证据边界

| 环境或证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 原型 | 需求、流程和交互意图已确认 | 实现符合原型、生产正常或用户已验收 |
| Agent 自验 | 本地实现、页面可访问和受影响路径已检查 | CI、用户验收或生产验收 |
| 本地测试 | 逻辑、契约和部分集成行为 | 托管权限、真实网络和生产数据 |
| CI `validate` | 固定提交通过仓库门禁 | 已部署、迁移已执行或生产正常 |
| Workers Builds | 该合并提交能构建并部署到生产 | 数据库兼容、用户验收或写链路正常 |
| 隔离 Supabase／Worker | 迁移、权限和真实 HTTP 链路 | 生产配置、真实用户和生产数据 |
| 生产只读探针 | 线上版本、页面和只读接口可用 | 写链路、回执和数据一致性 |
| 生产合成写入 | 指定范围的写链路和清理结果 | 未覆盖场景和长期稳定性 |
| 用户验收 | 用户确认需求和交互 | 生产部署和数据迁移已完成 |

本地通过、Agent 自验、CI、用户验收和生产验收必须分别记录，不能合并成“全部通过”。

## 合并门禁

合并到 `main` 前必须同时满足：

- 需求、范围、方案和验收依据可追溯；实现与已确认方案一致。
- 交付分级及依据已写入 Issue，授权覆盖当前变更。
- 密钥扫描、类型检查、构建、接口测试、安全回归和浏览器回归按影响执行；仓库已有对应自动检查时，不能因“看起来不影响”而跳过。确实不适用的检查需在 PR 写明原因。
- PR 的必需检查 `validate` 全部成功。`validate` 汇总当前工作流的全部依赖，任一依赖失败、取消或跳过都不能通过。
- 分支包含最新 `main`，冲突已解决并重新验证。
- 固定提交完成规范与需求双轴评审，问题闭环。
- 按 [开发与交付](git-workflow.md#界面验收)需要用户验收的变更已完成验收；验收通过不等于自动获得发布授权。
- PR 记录变更原因、行为影响、验证结果、未验证项、回退方式和授权范围。

常用本地命令：

```bash
npm run typecheck   # TypeScript 类型检查
npm run build       # typecheck + Vite 构建
npm run test:api
npm run test:security
npm run test:browser
```

`npm run types` 生成 Cloudflare 环境类型，不是类型检查。CI 以 `.github/workflows/ci.yml` 的实际依赖为准；本地检查按影响选择，但不能把本地选择当成 CI 豁免。

## 部署门禁

### 合并与自动部署

`main` 合并会触发 Cloudflare Workers Builds。由于部署在合并后自动发生，部署门禁实际上由两部分组成：

1. 合并前：`validate` 全部成功，候选提交、合并方式和目标分支已确认。
2. 合并后：核对 Workers Builds 成功，部署提交 SHA 等于本次合并 SHA，生产域名和绑定正确。

GitHub CI 与 Workers Builds 可能并行运行。不能把“GitHub CI 还在跑”当作部署已通过，也不能因为 Workers Builds 成功就跳过 `validate`。

### 多阶段发布

涉及迁移、停机或前后不兼容时：

- 在维护窗口内冻结 `main` 的其他合并，只允许当前候选 PR。
- 记录候选 PR 的 HEAD、目标分支和 merge-base，合并后核对实际合并 SHA。
- 部署失败、合并 SHA 不符或 `main` 已前进时，保持停机并重新核对，不手动部署另一个制品替代。
- 不使用强推、绕过分支保护或直接向 `main` 推送来修复发布。

## 兼容性与时序

先判断新代码与数据库的兼容关系，再决定顺序：

| 情况 | 默认顺序 |
|---|---|
| 新代码兼容旧数据库 | 迁移 → 验证 → 合并并部署 → 验证 → 恢复流量（如已停流） |
| 旧代码兼容新数据库 | 合并并部署 → 验证 → 迁移 → 验证 → 恢复流量（如已停流） |
| 两者互不兼容 | 停流 → 迁移或部署到兼容版本 → 验证 → 恢复流量；必要时先设计过渡版本或接受明确停机窗口 |
| 纯新增且旧代码不访问新对象 | 部署与迁移可交换，但仍须核对名称、权限、迁移历史和失败回退 |

“恢复流量”只适用于已停流的发布；未停流时跳过。纯新增且旧代码不访问新对象时，不要求停流。不能假设自动部署会按数据库门禁顺序发生。需要“先迁移再部署”时，必须在合并前确认迁移已完成并通过验证；迁移成功但 PR 未合并时，按已产生的对象和权限决定保留、停用或清理，并记录实际状态。

## 停机与停流

### 适用场景

- 新库与旧 Worker 不兼容。
- 需要原位修改或删除既有对象、数据或权限。
- 需要执行无法在运行中安全完成的迁移。
- 需要防止旧客户端、队列、重试或后台任务继续写入。
- 发生数据不一致、权限错误或未知事务状态。

### 停流清单

停机前逐项确认：

- 主域名、`workers.dev`、预览地址和自定义路由的实际可达性。
- 旧 Worker、新 Worker 和直连 Supabase RPC／REST 的写入口。
- 浏览器重试、队列、采集器上传、定时任务和后台任务。
- 管理通道和运维脚本是否仍能写。
- 在途请求如何排空，超时和重试如何处理。
- 停流生效时间和证据。

仅关闭主域名不能证明写入已停止。直连数据库或 RPC、旧版本 Worker、预览地址和后台任务都可能继续写。

### 恢复条件

恢复流量前必须确认：

- 数据库、Worker 和前端属于同一兼容版本。
- 迁移事务已提交或已明确回滚，不存在事务状态不明。
- 关键对象、函数签名、权限、RLS 和迁移历史已核对。
- 受控探针通过，且能确认请求命中新版本。
- 回退点和回退方式明确，用户授权仍覆盖当前结果。

不满足时保持停机。不能因为“已经停了很久”而带病恢复。

## 数据库与迁移

### 迁移分类

| 类型 | 判断 | 默认门禁 |
|---|---|---|
| 纯新增 | 只新增 schema、表、函数及这些新对象的权限；索引仅限新建表上的索引；不改既有对象、既有数据或全局授权 | 记录受影响对象、权限、迁移历史和现网版本基线；停流可选；不要求全库备份 |
| 原位修改 | 修改既有表、函数、权限或数据，但保留兼容读取 | 可恢复备份和恢复演练；停写；单事务；部署兼容版本 |
| 破坏性变更 | 删除、重命名、重写既有对象或数据，或改变不可逆语义 | 可恢复备份和恢复演练；停流；明确数据保全、回退或前向修复 |

纯新增必须核对：

- 对象名称和命名空间没有与既有对象冲突。
- 只对新对象授权，不改变既有角色属性、成员关系或既有对象授权；给既有角色授予新对象权限属于纯新增。
- 扩展依赖已存在或由迁移显式创建。
- 迁移历史与实际执行一致。
- 旧 Worker 不会访问新对象，或已确认兼容。

发现既有对象重名、替换、全局授权或既有业务改写时，停止按纯新增处理，转入原位修改门禁。既有表加索引、修改既有函数或权限，同样按原位修改处理。

### 备份边界

纯新增迁移：

- 保存受影响对象、权限、迁移历史和现网版本基线。
- 不要求全库 `pg_dump`，也不因缺少数据库密码阻断。
- 不把对象清单或前向迁移脚本称为完整可恢复备份。
- 回退优先停用新入口、保留休眠对象，或在停写且确认无业务事实后删除本次精确新增的对象。

原位或破坏性迁移：

- 备份至少覆盖受影响 schema、数据、函数、权限／RLS、索引、约束和迁移历史；无法隔离影响面时按完整数据库备份处理。
- 在隔离目标执行恢复演练并核对定义、权限和关键数据。
- 备份不完整时补足或停止，不进入不可逆阶段。
- 恢复旧备份可能覆盖同期新事实，必须先停写、保存当前状态并取得明确授权。

### 单事务与分段

- 一个完整迁移文件优先一次传输、一个事务执行。
- SQL 自带唯一事务边界时，不再外包事务。
- 提交前在同一连接和事务内做断言：对象存在、函数签名正确、无旧引用、权限、RLS 和索引符合预期；断言失败直接回滚。
- 提交后核对迁移历史与仓库脚本一致，并做只读的整体验证。
- 只有传输上限确实无法覆盖完整文件时才允许分段。分段必须事先定义边界，保证不切断函数体或事务块，不留下“结构已迁移、函数仍引用旧表”的中间态。
- 分段执行导致迁移历史与仓库脚本不一致时，必须在执行前评估并记录，不能事后用“结果正确”合理化。

COMMIT 前失败时，确认整笔事务回滚。COMMIT 后失败时保持停机：纯新增优先停用入口、前向修复或删除精确新增对象；原位或破坏性变更按已发生事实决定前向修复或恢复备份。

## 回退

回退前先回答：

1. 是否已经产生新的业务事实？
2. 回退会覆盖哪些写入、回执、奖励或账单？
3. 回退目标是旧 Worker、旧数据、可恢复备份，还是关闭功能？
4. 是否需要停流、保存当前状态或用户授权？

原则：

- 未提交事务或未产生新事实时，优先恢复到上一已验证版本。
- 已产生新事实时，不能直接恢复旧备份或重放旧初始化；先停流并保存当前状态。
- 代码回退优先于整库恢复；数据问题优先前向修复，恢复备份是例外。
- 数据库结构变更后，不用删除既有表或重跑旧脚本代替回退。
- 纯新增对象可在停写、确认无业务事实并取得授权后精确清理；不得批量删除或影响既有对象。
- 任何破坏性回退、恢复生产备份或删除外部资源，都需要用户明确授权。

Cloudflare Worker 可回退到上一已验证版本。回退后仍需核对部署版本、生产域名、绑定和公开配置；KV 为最终一致存储，回退代码不等于立即撤销所有边缘已读取的值。

## 生产验收

生产验收按适用项至少记录：

- 生产 URL、部署 SHA、构建或版本标识。
- 如涉及页面，页面可访问且包含本次变更。
- 如涉及接口，相关只读接口返回预期结构，错误路径可识别。
- 登录、白名单、权限和密钥隔离未被破坏。
- 按 [开发与交付](git-workflow.md#界面验收)记录的适用用户验收结果。
- 写入链路的合成测试范围、回执、清理结果和残留检查。
- 未验证项、已知限制和后续处理。

只读 smoke 不能证明写链路。需要写入验收时，使用获准的测试身份和合成数据，不操作真实用户账单、冒险、Token 或凭据；结束后按预先审阅的范围精确清理，并核对没有范围外残留。

如已停流，恢复流量后观察错误率、延迟、重复请求和关键业务写入。发现异常时重新停流，根据是否已产生新事实决定回退路径。

## 完成定义与记录

发布完成需要同时满足：

- 合并 SHA 对应生产部署。
- 迁移（如有）已按计划完成，迁移历史与实际一致。
- 按适用项完成生产页面、接口、权限和数据核验。无运行时行为变更的文档发布记录部署 SHA 和生产资源／配置核验，并明确未改运行时行为。
- PR 记录发布结果、验证证据和未解决问题。
- Issue 记录最终状态并关闭。
- 工作区没有待保存内容或仍在使用的服务，再按 Orca 清理流程收尾。

发布记录模板：

| 项目 | 内容 |
|---|---|
| 变更与 Issue | 功能摘要、Issue／PR |
| 分级与授权 | 分级依据、用户授权范围 |
| 兼容与时序 | 新代码／旧库关系、迁移与部署顺序 |
| 合并与部署 | 合并 SHA、构建 ID、部署版本、时间 |
| 迁移与停机 | 迁移类型、事务结果、停流范围、恢复条件 |
| 验证 | 本地、CI、用户验收、生产核验分别记录 |
| 回退 | 回退点、回退方式、是否已使用 |
| 未完成项 | 阻塞、已知限制、后续任务 |

## 禁止事项

- 未取得具体授权就合并需确认的变更或执行生产操作。
- 为假想规模或假想故障增加兼容层、双写、自动回滚编排等过度防御代码。
- 用 CI、构建成功、Agent 自验或页面可访问代替生产验收。
- 在数据库与 Worker 不兼容时恢复流量。
- 只关闭主域名就宣称写入已停止。
- 用分段迁移、跳过错误或修改迁移历史掩盖执行问题。
- 把不完整备份称为完整可恢复备份。
- 在日志、Issue、PR 或聊天中暴露真实凭据、白名单或敏感业务数据。
